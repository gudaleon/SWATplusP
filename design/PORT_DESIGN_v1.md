# SWAT+P — Fortran port design v1 (2026-11-19)

Method: Researcher-led AI research.
This note records the porting decisions for implementing the frozen sorption core (`SORPTION_CORE_SPEC_v1.md`, pool-level tests in `README_v1.md`) inside the audited SWAT+ source, before any Fortran is written, so the mapping choices are on the record and reviewable. The audited source is never modified in place: the port is developed in a copy of the clone at commit 6f515368525e7d84089ae0f9d33f4c9115de5679, held in this folder as `swatplus_aug/`.

## Where the switch goes

The dispatch is in `hru_control.f90` (lines 406–410 of the audited commit): `if (bsn_cc%sol_P_model == 1) call nut_pminrl2, else call nut_pminrl`. The port adds one branch, `else if (bsn_cc%sol_P_model == 2) call nut_pminrl3`, and a new file `nut_pminrl3.f90` carrying the core. The stock routines are untouched, so sol_p_model 0 and 1 remain the controls, as the branch plan requires. The daily call order is favourable: the mineral routine runs before `nut_solp` (line 567), so the augmented routine can publish each layer's equilibrium concentration to a small module that `nut_solp` reads later the same day when the augmented branch is active.

## The pool mapping, decided and stated

SWAT+ carries three mineral pools per layer in kg P/ha (`soil1(j)%mp(l)%lab`, `%act`, `%sta`) and derives a solution concentration inside `nut_solp` from the labile pool through a linear partition. The frozen core carries a solution concentration, a fast-sorbed pool and a slow pool, with the Langmuir equilibrium between solution and fast pool. The port maps them as follows. The labile pool is the core's fast-sorbed pool, held in kg/ha and converted to and from mg/kg through the layer's soil mass (thickness and bulk density from the soil physical properties). The active pool is the core's slow pool, exchanging with the fast pool at the frozen ageing rates (0.0006 forward, 0.00006 back per day). The stable pool is outside the sorption core's scope: under the augmented branch it neither receives nor releases, and its initial content stays where initialisation put it, which is stated here as a porting limitation rather than hidden, because the frozen core has three pools and inventing a fourth behaviour would break the freeze. The solution concentration is not a SWAT+ state variable, so the augmented routine reconstructs it each day from the fast pool through the inverted Langmuir form, C_eq = M_f / (K_L · (S_max − M_f)), with the layer's water content setting the solution mass that the day's boundary fluxes (fertiliser in, uptake and leaching out, all of which act on the labile pool in other routines) imply; `nut_solp`'s partition is bypassed under the augmented branch in favour of that concentration, which is the one place outside `nut_pminrl3` the port touches, fenced by the same sol_p_model == 2 condition. Capacity and affinity (S_max, K_L) enter as two new basin parameters with the frozen values as defaults (683.5 mg/kg, 0.2 L/mg), per soil through the existing soil nutrient parameter route where the data structure allows, and as basin constants where it does not; which route the data structures support is a build-time fact to be recorded in the port's README, not decided here by preference.

## The watershed test

The comparison case is the Ames_sub1 configuration held by the SLC soil-layer project (`swatplus_backend/test1/run_ames`), which the stock release binary already runs on this machine. The augmented build runs the same inputs under sol_p_model 0, 1 and 2, and the comparison is reported per branch: soil phosphorus pool trajectories, solution concentrations, and the tile and runoff phosphorus fluxes, over a shortened window if the full 46 years is impractical, with the window stated. Two version facts are recorded in advance: the audited source is a development commit newer than the 62.0.1 release the Ames inputs were prepared for, so input-format drift is a possible build finding, and the prebuilt stock binary is the release build, not a build of the audited commit, so the control runs for the comparison are made with the branch's own stock build, not the prebuilt binary.
